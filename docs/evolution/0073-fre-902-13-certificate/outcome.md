# Outcome: FRE 902(13) Certification Document

## What was built

A complete FRE 902(13) certification PDF feature for WRL. Every completed capture with a WACZ bundle can now produce a downloadable certification document designed for US court proceedings.

### Deliverables

**API endpoint**: `GET /v1/captures/{captureId}/certificate`
- Returns a deterministic, Ed25519-signed PDF
- Public endpoint (no auth required), rate-limited via VERIFY_RATE_LIMITER
- Immutable caching (`Cache-Control: public, max-age=31536000, immutable`)
- Detached signature in `X-Signature-Ed25519` and `X-Signature-Key-Id` headers
- Content-Disposition triggers download with `certificate-{captureId}.pdf` filename
- Proper error responses: 404 (not found/no WACZ/cross-tenant), 451 (quarantined), 429 (rate limited)

**PDF document** (~2-3 pages, 6 sections):
1. Title: "Certification of Record Generated by Electronic Process or System"
2. Attestation: Blank fields for qualified person (name, title, signature) — designed for adoption, not pre-filled
3. Process Description: 7-step capture process, security controls, system overview
4. Integrity Evidence: SHA-256 hash, Ed25519 signature, RFC 3161 timestamp, eIDAS timestamp (conditional)
5. Operator Identity: Legal name, contact info, public key fingerprint
6. Verification & Disclaimer: Verification URL, legal disclaimer

**Web UI**: "Download Certificate (PDF)" button in the artifacts section of the capture detail view, conditional on WACZ presence, styled as ghost button.

**Documentation updates**: OpenAPI spec (full endpoint definition), legal-evidence.md (902(13) section), verification.md (cross-reference), README (one-line mention).

## What deviated from the plan

1. **FlateDecode compression**: The synthesis plan specified keeping content streams uncompressed for easy test string matching. In practice, pdf-lib always compresses page content streams with FlateDecode — `useObjectStreams: false` only controls cross-reference streams, not content streams. Resolution: added fflate's `unzlibSync` for test decompression with a byte-level stream extraction helper.

2. **Test helper complexity**: The initial string-boundary approach (`\nstream\n` indexOf on latin1 string) failed because binary compressed data could contain those byte sequences. Required a custom `findBytes` function operating directly on `Uint8Array` — more complex than expected but reliable.

3. **Operator info**: The synthesis plan suggested making operator info configurable via env vars. The implementation hardcodes operator details (legal name, address) since WRL is a single-operator system. This follows YAGNI — configurability can be added when a second operator exists.
