ADVISE

- [security]: `env._captureAuth` uses mutable env mutation, same as the established `env._session` pattern -- but unlike `env._session`, the `rawToken` is stored on it and flows into response body construction, creating a risk that future code accidentally logs or echoes it.
  SCOPE: `src/index.js` auth gate block; `env._captureAuth.rawToken`
  CHANGE: Do not store `rawToken` in `env._captureAuth`. Instead, pass it directly to the specific handlers that need to append it to URLs (handleGetCapture, handleCaptureStatus). Handlers should receive it as a function argument or via a narrower mechanism, not as a persistent field on a shared mutable object that survives the request lifecycle.
  WHY: The raw share token on `env._captureAuth` is readable by any handler that can read `env`. If a new handler is added later, or if a logging call inadvertently serializes `env._captureAuth`, the token leaks. The plan's own checklist says "raw share tokens are NEVER logged" -- storing the raw token on a shared object works against this invariant. The pattern for API keys in `auth.js` is instructive: raw tokens are never stored anywhere after hashing; only the hash prefix travels forward.
  TASK: Task 1

- [security]: The revocation endpoint uses a LIKE prefix match (`token_hash LIKE ?||'%'`) on a 16-character prefix to identify which token to revoke. An attacker who has compromised a share token and knows its prefix (8 chars are logged; 16 are in the URL) could potentially cause accidental revocation of the wrong token if two tokens for the same capture share a common 16-char prefix.
  SCOPE: `handleRevokeShare` in `src/index.js`; revocation endpoint `DELETE /v1/captures/{id}/share/{tokenHashPrefix}`
  CHANGE: Either (a) require the full 64-char hash in the revocation URL (the client already received it as `token_hash` via `listShareTokensForCapture`), or (b) add a `LIMIT 2` to the LIKE query and reject with 409 Conflict if more than one row matches. Option (b) degrades gracefully without changing the URL format. Option (a) is cleaner -- the plan's `listShareTokensForCapture` already returns the first 8 chars of `tokenHash` for display, so the full hash could be returned in the creation response and stored client-side. SHA-256 collision on the first 16 hex chars has negligible probability in practice, but the LIKE query is an inconsistency with the rest of the auth model (which does exact-match PK lookups), and exact-match is the safer default.
  WHY: The rest of the auth model is built on exact-match PK lookups (token_hash is the primary key). The LIKE-based revocation is the only fuzzy match in the system. Consistency with the exact-match pattern closes the ambiguity surface entirely. CWE-289 (Authentication Bypass by Alternate Name) is tangentially applicable -- if the prefix is short enough that two tokens could share it under adversarial token generation, the wrong token gets revoked.
  TASK: Task 1

- [security]: The plan specifies that expired tokens return `410 Gone` with `{"detail": "Share token has expired"}` -- a distinct response from invalid/revoked tokens. This is an acceptable disclosure (the spec justifies it), but the SECURITY.md threat analysis section should explicitly note that the 410 response confirms to an observer that a token *was* valid at some point. This is especially relevant in contexts where share URLs may be observed by intermediaries (proxy logs, CDN logs).
  SCOPE: Task 3 SECURITY.md "Threat Analysis" section
  CHANGE: Add an explicit note to the residual risks: "The 410 Gone response for expired tokens confirms to an observer that the token was once valid. This is an accepted trade-off to provide a useful error message to legitimate users. Mitigated by time-limiting tokens and the recommendation to use short expiry windows for sensitive shares."
  WHY: The plan mentions this risk under the 410 decision but the SECURITY.md task description for "Threat Analysis" doesn't explicitly call it out. SECURITY.md is the document operators read when assessing the system's security posture. Silent omission of a confirmed information leak (even an accepted one) is an A09 (Security Logging and Alerting Failures) adjacent gap -- operators can't make informed decisions about risk they don't know is accepted.
  TASK: Task 3

- [security]: The `isCaptureReadRoute` check uses `pathname.startsWith('/v1/captures/')` which will match POST routes like `/v1/captures/{id}/share`. The plan says POST endpoints are excluded because "they already have auth inside the handler" and says to add the gate "AFTER the account-route gate and BEFORE route dispatch". The gate block wraps itself in `if (!response && isCaptureReadRoute)` and the method check is `request.method === 'GET'` -- so POST is already excluded by the method check. However, the `isCaptureReadRoute` variable name is misleading: it is true for ALL methods on `/v1/captures/*`, and the gate's method filter is buried inside the condition rather than in the variable definition. If a developer later adds a `PUT` or `PATCH` handler and checks `isCaptureReadRoute` to decide whether to apply any logic, they will get a false signal.
  SCOPE: `src/index.js` auth gate block; `isCaptureReadRoute` variable
  CHANGE: Rename to `isCaptureGetRoute` and include `request.method === 'GET'` in the variable definition itself, consistent with how the variable is used. This makes the intent unambiguous and prevents future misreads. Alternatively, inline the full condition rather than extracting it to a variable.
  WHY: Security-critical routing logic should be as explicit as possible. Naming a variable "read route" but having it match POST paths is a readability trap that could lead to a future privilege escalation bug when someone adds a new verb and copies the guard incorrectly. This is A01 (Broken Access Control) risk: a misleading abstraction that might cause a future developer to skip the auth gate for a mutation.
  TASK: Task 1

- [security]: The share token creation endpoint (`POST /v1/captures/{id}/share`) allows creation for captures in `pending` status. If a capture subsequently fails, the share token remains valid (targeting a failed capture). The plan says `handleGetCapture` will return the record regardless of status, and the auth gate enforces tenantId ownership -- so a share token for a failed capture would return the metadata of the failed capture. This is not a critical vulnerability (the data is the tenant's own), but it leaks that a capture exists and failed to any share token recipient. The plan explicitly says "Allow share creation for pending and complete captures (not failed)" but does not handle the case where a pending capture's share token is used *after* the capture transitions to failed.
  SCOPE: `handleGetCapture` and share token validation in auth gate
  CHANGE: When a share token is used to access capture metadata, check `record.status !== 'failed'` and return 404 if the capture failed. Or document this as an accepted behavior in the SECURITY.md threat analysis ("Share tokens for pending captures remain valid if the capture fails; recipients see the failed capture metadata"). The 404 approach is cleaner and consistent with the "share tokens for failed captures" restriction on creation.
  WHY: The intent of the per-status creation restriction ("not for failed captures") should be consistent at access time, not just at creation time. If it's a policy decision to not share failed captures, the policy should be enforced when the token is *used*, not only when it is *created* (since a capture can fail after a token is created for it in pending state). This is a data integrity / information disclosure issue: the share recipient shouldn't receive a failed-capture response if the creating tenant intended to share only successful ones.
  TASK: Task 1
