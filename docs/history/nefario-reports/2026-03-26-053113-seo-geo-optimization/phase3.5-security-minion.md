ADVISE

- [security]: Nunjucks template variables interpolated directly into a `<script type="application/ld+json">` block are not JSON-escaped, creating a JSON injection vector.
  SCOPE: `site/_includes/layouts/base.njk` — the proposed WebSite JSON-LD block using `{{ site.title }}`, `{{ site.docsUrl }}`, and the OG/Twitter tags using `{{ title }}` and `{{ description or site.description }}`
  CHANGE: JSON string values interpolated into `<script type="application/ld+json">` must be JSON-escaped, not just HTML-escaped. Nunjucks `{{ }}` applies HTML auto-escaping in HTML contexts but does NOT apply JSON escaping inside `<script>` blocks. A `title` or `description` frontmatter value containing a double-quote character (`"`) will produce malformed JSON. A value containing `</script>` will break out of the script block entirely. Two mitigations are viable: (1) use only values sourced from `site.js` (a developer-controlled JS file, not arbitrary user frontmatter) in the JSON-LD block — the proposed WebSite block uses only `site.title` and `site.docsUrl`, both from `site.js`, so this is already safe for that block; (2) for any JSON-LD that would interpolate per-page `title` or `description` frontmatter in the future, add a Nunjucks filter that JSON-encodes the value (e.g., `{{ title | dump }}`). The plan as written only puts `site.title` and `site.docsUrl` in JSON-LD (both safe, developer-controlled), but the implementation agent should be explicitly told NOT to interpolate per-page `title` or `description` frontmatter into JSON-LD without a `dump` filter. This constraint is not stated in the current Task 1 prompt.
  WHY: If a docs page author writes a `description` like `WRL: "fast" evidence API` in frontmatter and that value is later interpolated into JSON-LD, it produces invalid JSON that search engines reject. If the value contains `</script>`, it breaks out of the script block and could be interpreted as inline HTML. The current Task 1 JSON-LD block happens to use only site-level data (safe), but the implementation prompt does not say this explicitly — the agent could reasonably extend the pattern to per-page data.
  TASK: Task 1

- [security]: The `{{ content | safe }}` filter in `base.njk` passes Markdown-rendered content unsanitized into HTML — this is existing behavior and acceptable for a developer-controlled docs site, but it means any Markdown content page can inject arbitrary HTML including `<script>` tags. This is not introduced by the SEO changes, but the SEO changes add new frontmatter fields (`description`, `noindex`) that flow into meta tags. A `description` containing `">` could break out of the `content` attribute if the implementing agent uses unquoted or single-quoted attribute values.
  SCOPE: `site/_includes/layouts/base.njk` — the proposed `<meta name="description" content="{{ description or site.description }}">` and OG/Twitter meta tags using the same pattern
  CHANGE: Verify the meta tag attributes use double-quoted values (they do in the plan's sample HTML — `content="{{ ... }}"`) and that Nunjucks auto-escaping is enabled (it is by default in Eleventy). This is already correct in the plan as written; the implementation agent should not deviate to unquoted or single-quoted attribute values. Add a note to Task 1 to keep double-quoted attribute values for all meta tags.
  WHY: Nunjucks auto-escaping converts `"` to `&quot;` in HTML attribute contexts, preventing attribute breakout. This protection depends on the attribute being double-quoted with standard `{{ }}` interpolation (not `| safe`). The plan's examples are correct; this is a verification note to ensure the agent doesn't accidentally use `| safe` on description values.
  TASK: Task 1
