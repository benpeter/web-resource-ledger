## Summary

Production CD pipeline for WRL implemented as a single GitHub Actions workflow
(`deploy-production.yml`) with three sequential jobs: staging smoke gate, deploy
with environment protection approval, and production smoke test. Accompanied by
an operations runbook (`OPERATIONS.md`) covering deploy flow, rollback procedures,
and environment setup. Three key conflicts resolved by favoring simplicity: self-
contained staging gate over workflow_run, push-to-main over tag triggers, and
deferred smoke test enhancements as YAGNI.

## Original Prompt

#44 R14: Production CD pipeline with environment protection.

Outcome: Production deployments are reproducible, gated by approval, and have
rollback capability — required before external users depend on WRL uptime.

Success criteria: GitHub Actions production workflow, environment protection
rules, post-deploy health check, rollback documentation, staging-must-pass gate.

## Key Design Decisions

1. **Staging gate: self-contained workflow** — Staging smoke as Job 1 inside the
   production workflow, not a `workflow_run` trigger. Single Actions run shows
   full pipeline. Tradeoff: validates staging health, not code parity.

2. **No tag triggers** — `push: branches: [main]` + `workflow_dispatch` only.
   Tags add cognitive load and security surface for a solo developer. Deferred
   to backlog.

3. **Smoke test reuse** — Existing `smoke-test.sh` used as-is with
   `SMOKE_SKIP_CAPTURE=1` for production. Version check and response time
   assertions deferred as YAGNI.

4. **Separate Cloudflare tokens** — Production and staging each have their own
   `CLOUDFLARE_API_TOKEN` scoped to GitHub environments.

5. **No `[env.production]` in wrangler.toml** — Top-level config is already
   production. Adding an env block would change the Worker name.

## Decisions

### Conflict 1: Staging gate mechanism
- **iac-minion**: Self-contained (staging smoke in production workflow Job 1)
- **test-minion**: `workflow_run` trigger from staging workflow
- **Resolution**: Self-contained. Single workflow run is easier to observe. Code parity tradeoff acceptable for solo project.

### Conflict 2: Tag triggers
- **iac-minion**: Both `v*` tags and `workflow_dispatch`
- **ux-strategy-minion**: Tags are unnecessary cognitive load for solo developer
- **security-minion**: Tags introduce security surface (mutation, non-main commits)
- **Resolution**: No tags. Push-to-main + workflow_dispatch only.

### Conflict 3: Smoke test enhancements
- **test-minion**: Add version check and response time assertion
- **Resolution**: Both deferred as YAGNI with backlog activation triggers.
