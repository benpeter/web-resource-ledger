## Security Review: Scheduled Captures / Cron Feature

**Verdict: ADVISE**

---

[security]: Cron expression DoS via pathological intervals, SCOPE: Task 2 / src/cron.js, CHANGE: The minimum-interval check fires only 5 consecutive times forward. A cron like `0 0 1 2 *` (Feb 1 annually) produces consecutive gaps of 8,760+ hours -- well above the 60-minute floor -- and passes. But consider `0 0 29 2 *` (Feb 29): croner may produce distant or no-op times, and the loop over 5 future fires might silently succeed or throw. More importantly, certain valid expressions can produce extremely long computation times if croner enumerates far-future dates. Hard-cap the validation loop with a 200ms wall-clock guard or limit nextN() calls to expressions that fire within a 2-year lookahead window. WHY: A tenant can store a cron that stalls the Worker tick if croner iterates deeply for each fire-time calculation in `nextRunAfter`, or stalls the validation endpoint itself. TASK: In `validateCron()`, add a try/catch around the nextN call with a maximum lookahead of 2 years; return `{ ok: false, detail: 'Cron expression produces no scheduled runs within 2 years' }` if fewer than 2 fires are found in that window.

[security]: TOCTOU race on schedule limit allows limit bypass via concurrent creation, SCOPE: Task 2 / handleCreateSchedule, CHANGE: The schedule count check (`countSchedules` + comparison) and the `createSchedule` INSERT are two separate D1 operations. A tenant that fires N concurrent POST /v1/schedules requests can race past the limit check. The existing `countWebhooks` pattern in webhooks.js has the same gap. To fix: add a UNIQUE constraint or an application-level gate that runs the count and insert atomically. The cleanest D1-compatible approach is a `WITH` CTE: `WITH check AS (SELECT COUNT(*) AS n FROM schedules WHERE tenant_id = ?) INSERT INTO schedules SELECT ... WHERE (SELECT n FROM check) < ?`. Alternatively, add a CHECK trigger on the table that raises SQLITE_CONSTRAINT if the count exceeds the limit -- though triggers are harder to test. At minimum, document the race as an accepted risk if not fixing now. WHY: Without atomicity, a motivated tenant can overprovision schedules, bypassing per-tenant limits and enabling resource exhaustion via the scheduled() fan-out. TASK: Evaluate whether a CTE-based atomic insert is feasible in D1 (SQLite 3.35+); if yes, implement it in `createSchedule`; if not, add it to the backlog as a known race with a note that the blast radius is bounded by the fan-out quota check.

[security]: Scheduled handler creates captures and increments usage BEFORE the queue enqueue succeeds, SCOPE: Task 3 / src/scheduler.js, CHANGE: The fan-out flow is: createCapture -> incrementUsage -> sendBatch. If sendBatch fails, captures are created as 'pending' and usage has been charged, but no queue message was sent -- the capture will never complete. The plan acknowledges these as "orphans" and says not to call failCapture. This is a billing integrity issue: usage was incremented for a capture that will never run. The fix is either: (a) move incrementUsage to AFTER the queue message is acknowledged (queue.send is async, so you know it succeeded before incrementing), or (b) have the queue consumer call incrementUsage instead of the scheduler. Option (b) aligns better with existing capture flow. WHY: Orphaned captures inflate a tenant's quota consumption without delivering the service. For paid tenants using metered billing this is a financial accuracy issue; for free tenants it eats into their monthly allowance unfairly. TASK: Move `incrementUsage` call from the scheduler to the queue consumer (`handleCaptureMessage`), or ensure `incrementUsage` is only called after `sendBatch` confirms receipt for that message.

[security]: Null IP in capture record leaks metadata about capture origin path, SCOPE: Task 3 / src/scheduler.js, CHANGE: Scheduled captures are created with `ip = null`. The plan passes `cip: 'cron'` as the client IP field in the queue message. Verify that `handleCaptureMessage` in index.js does not log or expose this null IP anywhere that a tenant can retrieve it, and that the capture detail API response omits or masks the null rather than exposing it as a distinguishable sentinel. This is low severity but worth confirming -- the null IP distinguishes automated captures from user-initiated ones, which could be used for fingerprinting if the API ever returns it. WHY: A03 / information disclosure. The IP field, even null, reveals capture origin metadata. TASK: Confirm that `rowToCapture` either omits `ip` from the JSON response entirely or that the API spec intentionally includes it as nullable; document the decision in openapi.yaml.

[security]: schedule_id filter on captures list lacks format validation before SQL binding, SCOPE: Task 2 / handleListCaptures in src/index.js, CHANGE: The plan adds `AND schedule_id = ?` to the capture list SQL when a `schedule_id` query parameter is present. The plan correctly uses parameterized queries (following existing patterns), so SQL injection is not a risk. However, the plan does not mention validating the `schedule_id` value against `SCHEDULE_ID_RE` before binding. Without format validation, a tenant could pass an arbitrary string and get a valid but empty result set -- no harm, but it adds noise to logs and bypasses the input contract. WHY: Defense in depth; consistent with how other ID parameters are validated (e.g., webhook IDs are regex-matched in route patterns before handler invocation). TASK: In the schedule_id filter block in handleListCaptures, validate the value matches `SCHEDULE_ID_RE` (from db.js) before binding; return 400 if not. This is low priority but costs one line.

[security]: Missing rate limiting on PATCH /v1/schedules (pause/resume endpoint), SCOPE: Task 2 / src/index.js route registration, CHANGE: The plan maps `/v1/schedules` to the `'capture'` rate limit group, which covers POST, GET, and DELETE. However, the PATCH endpoint for pause/resume is not explicitly mentioned in the rate limit group mapping. Confirm that the regex `^\/v1\/schedules` in `getRateLimitGroup` matches PATCH requests on `^\/v1\/schedules\/(sch_[a-f0-9]{32})$` as well. If the rate limiter groups by path prefix, PATCH is covered; if it groups by the exact route regex, it may not be. WHY: A motivated attacker with a valid key could rapidly toggle pause/resume to generate log noise or probe timing side-channels. TASK: Verify in `getRateLimitGroup` that the schedule path mapping covers all HTTP methods including PATCH; add explicit PATCH coverage if the current matching logic would miss it.

---

### Summary

No blocking issues. The design is sound: SSRF protection reuses the existing well-tested `validateUrl()`, IDOR protection is baked into every db.js function via tenant_id filters, and CAS-based `advanceSchedule` prevents duplicate fan-out. The five advisories above are ranked: (3) billing integrity is the most significant and should be resolved before launch; (2) limit race is low blast-radius but worth a backlog entry; (1) cron DoS is edge-case but fixable cheaply; (4) and (5) are informational.
