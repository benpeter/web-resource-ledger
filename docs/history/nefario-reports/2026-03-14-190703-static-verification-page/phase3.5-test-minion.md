- [test-minion]: Unit test case 23 checks for the string "innerHTML" inside the template, but this is a static string search that will produce a false negative if the implementation uses a variable assignment pattern like `el.innerHTML = ...` where the method call is correct but not matching the naive pattern check.
  SCOPE: test/verify-page.test.js, test case 23 ("does not contain innerHTML")
  CHANGE: The assertion should search for `innerHTML` as an assignment target (e.g., `.innerHTML`) not just the bare string, and should clearly comment that it is scanning the module source text — not the rendered HTML string. The test should import the raw source text (or read the file) rather than scanning `await response.text()`, because the `<script>` block in the HTML output may or may not reproduce the full module source.
  WHY: If the implementation correctly avoids `innerHTML` in the inlined `<script>` block but the word "innerHTML" is absent from the rendered HTML string (e.g., because the template only embeds a minified or partial copy of the logic), the test passes for the wrong reason. Conversely, if the template happens to include a comment mentioning innerHTML, the test fails spuriously. The intent is to guard against a developer later adding `el.innerHTML = fetchedData` — that intent is best expressed by reading the source file directly.

- [test-minion]: The integration test suite (Task 4) does not include a test verifying that the inline JS in the HTML page sets `Accept: application/json` on its same-origin fetch. Without this, a regression that removes the Accept header from the JS fetch would cause the page's client-side fetch to trigger the HTML branch of content negotiation (returning HTML instead of JSON to the JS), creating a silent infinite-render loop that no existing test would catch.
  SCOPE: test/verify-html.test.js, content negotiation regression section
  CHANGE: Add a test that reads the HTML response body text and asserts it contains the string `Accept: application/json` (or `'application/json'`) within a fetch call context. A `toMatch(/fetch.*Accept.*application\/json/s)` or `toContain("application/json")` string assertion on the HTML body is sufficient and consistent with the project's no-DOM-parser policy.
  WHY: The plan identifies this as a High severity risk ("Content negotiation loop: page's JS fetch gets HTML instead of JSON") and notes that integration test case #8 covers it. But test case #8 as written (`Accept: application/xml` -> returns JSON) tests the Worker's routing logic, not whether the HTML template's embedded JS actually includes the correct header. These are different failure modes. The static string check on the rendered HTML body directly verifies the template contains the required header string.
  TASK: Task 4

- [test-minion]: The integration tests require `beforeEach` to call `performCapture` for every test, including tests that only check header routing (tests 1-9, 17-20). `performCapture` is the expensive setup path (creates WACZ, signs it, writes to R2). Running it for 25 tests will make this suite noticeably slow compared to the existing pattern in `verify-integration.test.js`, which also uses it but for a smaller test count. More importantly, tests 24-25 (error paths with Accept: text/html) need a capture ID that does NOT exist — they currently depend on the `beforeEach` capture being deleted or using a different ID, which the prompt does not specify.
  SCOPE: test/verify-html.test.js, beforeEach setup and error path tests 24-25
  CHANGE: Clarify in Task 4 that error path tests (404 and 429 cases) must use a different, non-existent capture ID (e.g., `cap_` + `0`.repeat(32)) that is never created in `beforeEach`. Separate the error path tests into their own describe block with a note that they do not need a valid capture. This avoids test interference and makes the intent clear. For the 429 test, note that the rate limiter environment binding may not be active in the test environment (same caveat as the existing auth tests), and the test may need to be skipped or marked accordingly.
  WHY: Error path tests that inadvertently use the beforeEach capture ID will return 200 HTML instead of the expected error JSON, making them fail for the wrong reason. A test that expects a 404 but gets a 200 HTML page will fail with a confusing assertion error rather than a clear "this capture exists" message.
  TASK: Task 4

- [test-minion]: Neither the unit tests (Task 3) nor the integration tests (Task 4) verify that the URL scheme validation in the inline JS (`javascript:` scheme blocking on `<a href>`) is present in the template. This is one of the two explicitly called-out security controls in the Task 1 prompt ("only allow http: and https:"), yet it has no corresponding test assertion.
  SCOPE: test/verify-page.test.js, security section
  CHANGE: Add a unit test that asserts the HTML body contains a URL scheme check. A string assertion like `expect(html).toMatch(/href.*javascript/i)` or `expect(html).toContain("http:")` within a conditional context is sufficient. The test does not need to execute the JS — it just needs to confirm the template contains a scheme guard, similar to the existing innerHTML check pattern.
  WHY: Without a test, a future refactor that simplifies the URL rendering code (e.g., removing the scheme check to "clean up" logic) would pass all tests while silently removing a security control. The unit test makes the intent explicit and protects against regression.
