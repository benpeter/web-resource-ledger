# Accessibility Review: Static Verification Page
**Reviewer**: accessibility-minion
**Verdict**: ADVISE

The plan demonstrates strong accessibility awareness -- `<html lang="en">`, semantic landmarks, `.sr-only` pattern, SVG `aria-hidden`, descriptive alt text template, `prefers-reduced-motion`, and `:focus-visible` are all explicitly specified. Four issues require attention before or during Task 1 implementation.

---

- [accessibility]: `--color-text-muted` (#757575) fails WCAG 1.4.3 AA contrast on `--color-surface` (#fafafa) at 4.41:1, below the 4.5:1 minimum required for normal-weight text at 13px.
  SCOPE: `src/verify-page.js` -- CSS custom property `--color-text-muted` and `--color-surface`
  CHANGE: Either darken `--color-text-muted` to #767676 or darker (minimum to achieve 4.5:1 on #fafafa is approximately #767676 at 4.54:1, or safely #6d6d6d at ~5.0:1), or ensure that any element using both `--color-text-muted` and `--color-surface` together uses a white (#ffffff) background instead. The same issue applies when `--color-skip` (#757575) SVG icons appear on `--color-surface`. Additionally, `--color-text-muted` on `--color-pass-bg` (#e8f5e9) is 4.10:1 and on `--color-fail-bg` (#fce4ec) is 3.83:1 -- if detail text or skip-status text ever appears inside the colored badge area, it will also fail. Confine muted text to white backgrounds, or adjust the muted color value.
  WHY: WCAG 2.2 SC 1.4.3 Color Contrast (Minimum), Level AA. The 13px muted text used for check detail lines (the "second line in muted text" described in the plan) is the highest-risk location. If check rows render on `--color-surface` rather than on white, this is an AA violation that automated tooling (axe, Lighthouse) will flag and that visually impairs low-vision users.
  TASK: Task 1 (HTML Verification Page Module)

- [accessibility]: The loading state is described as a "CSS-only spinner or pulsing dots" that is replaced with content once fetches complete. No `aria-live` region is specified, so screen readers will not announce when verification results become available after the client-side fetch resolves.
  SCOPE: `src/verify-page.js` -- the JS loading-to-content transition and the `<main>` content area
  CHANGE: Add `aria-live="polite"` to the container element that transitions from loading state to result content, or add a visually hidden status announcement element (e.g., `<p class="sr-only" aria-live="polite" id="status-announce"></p>`) that the JS populates with "Verification result loaded" (or the verification outcome) once both fetches resolve. The loading spinner element itself should have `role="status"` and `aria-label="Loading verification result"` so screen readers announce the wait state. The CSS spinner must also respect `prefers-reduced-motion` (the plan mentions disabling transitions but an animated spinner that is simply hidden via `display:none` when motion is reduced may not fully address this -- replace it with a static indicator under `prefers-reduced-motion: reduce`).
  WHY: WCAG 2.2 SC 4.1.3 Status Messages (AA). When a screen reader user lands on this page, the loading state is invisible to them and the content swap is silent. Without a live region, a screen reader user on NVDA or VoiceOver will hear silence until they manually navigate the page to discover the result has loaded -- the experience is broken, not merely degraded.
  TASK: Task 1 (HTML Verification Page Module)

- [accessibility]: The plan specifies heading hierarchy as "h1 (status), h2 (each section)" but the status banner renders its content only after client-side JS executes. During the loading state and in the `<noscript>` fallback, there is no h1 in the DOM (or a loading placeholder h1 must be planned). The plan does not specify what the h1 contains during loading or how it transitions to the verified/unverified status heading.
  SCOPE: `src/verify-page.js` -- h1 element and heading lifecycle during loading state
  CHANGE: The h1 should be present in the initial HTML with either a static placeholder text (e.g., "Loading verification result...") that JS updates once data arrives, or a static title like "Capture Verification" that remains fixed while JS injects the status badge separately. The approach of using the h1 to announce status is correct in principle, but the heading must exist and be meaningful before JS resolves. Specify in Task 1 what the h1 reads during loading and how it is updated (via `textContent` reassignment is fine). Screen reader users who read the page immediately on load will encounter an empty or missing h1 without this.
  WHY: WCAG 2.2 SC 1.3.1 Info and Relationships (A) and SC 2.4.6 Headings and Labels (AA). An h1 that is absent or empty during load violates the semantic structure requirement and confuses screen reader navigation. NVDA and VoiceOver both announce headings immediately upon page load -- if the h1 content is absent at that moment, the page title is the only structural anchor for blind users.
  TASK: Task 1 (HTML Verification Page Module)

- [accessibility]: The `<details>/<summary>` element for cryptographic details is described as "collapsed by default" and "works without JS." No keyboard interaction note or accessible name for the `<summary>` is specified. Additionally, the plan does not specify what the `<summary>` visible label reads.
  SCOPE: `src/verify-page.js` -- `<details>/<summary>` cryptographic details section
  CHANGE: Specify the `<summary>` label text explicitly (e.g., "Cryptographic details" or "Show cryptographic details"). No ARIA is required -- `<details>/<summary>` has native keyboard support (Enter/Space to toggle) and browser-native accessibility tree mapping. The only risk is if CSS hides the default disclosure triangle in a way that removes the visual affordance; if the disclosure marker is styled away, add a visible custom indicator. Confirm the `<summary>` is the first child of `<details>` (some older browser/AT combinations require this for correct role mapping).
  WHY: WCAG 2.2 SC 4.1.2 Name, Role, Value (A). The `<details>/<summary>` pattern is well-supported but requires a meaningful `<summary>` label for screen readers to announce the toggle affordance correctly. This is a minor implementation gap -- native HTML handles it correctly if the label is present and the element is not over-styled.
  TASK: Task 1 (HTML Verification Page Module)
