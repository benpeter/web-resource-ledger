## Security Review: Content Security Scanning Delegation Plan

**Verdict: ADVISE**

The plan is well-considered and several correct security calls were already made upstream (Web Risk over Safe Browsing v4, provider-agnostic field naming, fail-open as defense-in-depth not a security boundary, Ed25519 preservation). The concerns below are actionable gaps that should be addressed before or during implementation.

---

[security]: API key exposure in URL query string — SCOPE: Task 2 (src/threat-check.js), CHANGE: The Web Risk Lookup API call passes the API key as `&key=<API_KEY>` in the query string (`GET https://webrisk.googleapis.com/v1/uris:search?uri=...&key=...`). Query string parameters appear in HTTP access logs, server-side access logs at Google, Cloudflare request logs, and any network inspection tools. WRL's own Coralogix logging may capture request URLs. This is a GOOGLE_WEB_RISK_API_KEY exposure vector., WHY: Google's own documentation recommends using the `X-Goog-Api-Key` request header for API key authentication instead of the `key` query parameter when making server-side calls. The query string approach is only documented for simplicity in quickstart examples. Using the header eliminates the key from logs and access traces., TASK: In `src/threat-check.js`, build the endpoint URL WITHOUT the `key` param: `https://webrisk.googleapis.com/v1/uris:search?uri=${encodeURIComponent(url)}&threatTypes=MALWARE&...`. Add the key as a request header instead: `headers: { 'X-Goog-Api-Key': env.GOOGLE_WEB_RISK_API_KEY }`. Also verify in the observability task (Task 5) that log events do NOT include the API request URL (which would leak the key if the header approach is not adopted).

[security]: Race condition on quarantine gate during concurrent reads — SCOPE: Task 3 (handleGetCaptureArtifact, handleVerifyCapture), CHANGE: The quarantine enforcement pattern is two sequential DB reads: (1) fetch record, (2) check `record.quarantined`. If `quarantineCapturesByUrl` runs between the fetch and the gate check — which is possible during the cron window — the artifact is served for captures that were quarantined mid-flight. This is a TOCTOU on a security-relevant gate., WHY: WRL's architecture is a Worker with D1. D1 reads are not isolated in a transaction here. The re-scan cron quarantines by URL (bulk), meaning multiple captures flip simultaneously. The window is small but nonzero. For a tamper-evident archival product the gate must be exact., TASK: This is low-risk in practice (the re-scan runs at 03:00 UTC and the window is milliseconds), but document it as an accepted residual risk in the evolution log. For the artifact handler specifically, consider a single-query pattern: `SELECT * FROM captures WHERE id = ? AND quarantined = 0 AND status = 'complete'` rather than fetching and then checking in JS — this makes the quarantine gate atomic at the DB level with no extra round-trip.

[security]: Fail-open attack window is under-alerting for pre-capture failures — SCOPE: Task 3 and Task 5, CHANGE: The plan correctly logs `threatcheck.api_fail` at severity 4 (warn) for pre-capture degraded checks and severity 5 (error) for the block case. However, the observability task alert threshold for API failures is "> 2 events in 10 minutes" for pre-capture context. An attacker who discovers the fail-open behavior (e.g., by causing API errors or exhausting quota) could target captures during the degraded window. The 10-minute window with threshold 2 means they could submit up to 2 malicious captures before alerting fires., WHY: The fail-open design is correct per Helix Manifesto (availability > screening), but the alert should fire on the FIRST API failure in the pre-capture path, not after 2 in 10 minutes. Sustained API unavailability is when abuse is most likely. The alert is the only compensating control during degradation., TASK: In Task 5 (provision-alerts.sh), change the pre-capture API failure alert threshold from > 2 in 10 minutes to >= 1 in 5 minutes. This is a tighter compensating control for the accepted fail-open risk. Also confirm that `threatcheck.api_fail` log events for the `pre_capture` context include the tenantId and keyHashPrefix fields (Task 3 prompt has a `??` placeholder at line ~344 — ensure these are actually populated, not undefined).

[security]: threatTypes input not validated before DB write — SCOPE: Task 1 (quarantineCapture, quarantineCapturesByUrl) and Task 4 (rescan.js), CHANGE: The `quarantine_reason` column stores threat types from the Web Risk API response (e.g., `threatTypes.join(',')`). The plan does not specify validation or allowlisting of the threat type strings before they are stored in D1 and returned in API responses. Google Web Risk returns values like `MALWARE`, `SOCIAL_ENGINEERING`, `UNWANTED_SOFTWARE` — but if the response parsing is loose (e.g., if a compromised/future response contains unexpected values), unvalidated strings flow into DB and API output., WHY: LLM05/A05 principle: treat external service responses as untrusted input. The threat types are displayed in API responses (`quarantineReason` field) and logged. An unexpected value won't cause SQL injection (prepared statements are used), but could cause confusion in alerting, expose unexpected data in API responses, or create a stored-injection vector if values were ever rendered in a UI context., TASK: In `src/threat-check.js`, add an allowlist validation after parsing the Web Risk response: `const KNOWN_THREAT_TYPES = new Set(['MALWARE', 'SOCIAL_ENGINEERING', 'UNWANTED_SOFTWARE', 'SOCIAL_ENGINEERING_EXTENDED_COVERAGE']); const validatedTypes = (threatTypes || []).filter(t => KNOWN_THREAT_TYPES.has(t));`. Return the filtered list. If `validatedTypes` is empty but `threat` was present in the response, return `{ safe: false, threatTypes: ['UNKNOWN'] }` rather than an empty array (which could be misread as safe). Document the known types list as needing periodic review against the Web Risk API docs.

[security]: Missing API key presence check does not distinguish "absent" from "zero budget" — SCOPE: Task 2 (threat-check.js), CHANGE: Test case 7 requires that when `env.GOOGLE_WEB_RISK_API_KEY` is undefined, the function returns `{ safe: true, degraded: true }`. This is correct. However, the degradation path for a missing key is silent — the log event at the call site in index.js (Task 3) only fires when `threat.degraded` is true, logged as `threatcheck.api_fail`. A permanently missing key (misconfiguration, deployment error) will produce continuous degraded captures with no distinct signal separating "key is missing" from "Google API is down"., WHY: Operators need to distinguish a misconfiguration (key was never set, or a secret was lost during deployment) from a transient Google outage. Currently both produce the same `threatcheck.api_fail` event. The runbook for API failures (Task 5) recommends checking Google Cloud Console quota — but if the key is simply absent, that check is a red herring., TASK: In `src/threat-check.js`, before making the API call, check if the key is absent: if so, return `{ safe: true, degraded: true, reason: 'no_api_key' }`. In the call-site logging in `index.js` (Task 3), include the `reason` field in the `threatcheck.api_fail` log event. The runbook for API failures (Task 5) should list "API key missing or not injected" as the first likely cause and distinguish it from quota/outage.

---

### Summary

None of these are blocking concerns — the architecture is sound, the fail-open decision is correct for this product, and the threat-check module is properly isolated. The highest-priority item is (1) the API key in query string, which should be a header before any staging deployment. Items (2)-(5) are hardening improvements that can land in the same PR. The race condition in item (2) is accepted residual risk but should be documented.
