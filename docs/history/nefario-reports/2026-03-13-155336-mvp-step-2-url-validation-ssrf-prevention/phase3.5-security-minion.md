- [security-minion]: IPv4-mapped IPv6 in hex-group notation (::ffff:7f00:0001) is not covered by the implementation guidance or test suite, creating a bypass vector.
  SCOPE: src/url-validation.js -- isPrivateIP() IPv6 handling; test/url-validation.test.js -- IPv6 private ranges describe block
  CHANGE: The implementation must handle ::ffff:7f00:0001 (pure hex-group form of ::ffff:127.0.0.1) in addition to the dotted-decimal form. The WHATWG URL constructor normalizes [::ffff:7f00:1] to the hostname ::ffff:7f00:1 -- not ::ffff:127.0.0.1 -- so the IPv4 extraction logic cannot rely on dotted-decimal form being present. The implementation prompt specifies "extract and re-check IPv4 portion" but does not specify how to detect and parse the hex-group form. Add this explicitly: when the last 32 bits of an IPv4-mapped IPv6 address are in two 16-bit hex groups (e.g., 7f00:0001 = 127.0.0.1), extract the two groups, shift-combine them into a 32-bit integer, and run through the standard IPv4 private range check. The test suite must add a case: ['IPv4-mapped loopback hex-group', 'http://[::ffff:7f00:1]/'].
  WHY: A browser (Chromium) navigating to http://[::ffff:7f00:1]/ will connect to 127.0.0.1. The WHATWG URL constructor renders this hostname as ::ffff:7f00:1 not ::ffff:127.0.0.1. If isPrivateIP() only extracts the IPv4 portion from dotted-decimal notation, this form passes the blocklist check and produces a full SSRF bypass against localhost.
  TASK: Task 1 (implementation prompt), Task 2 (test suite)

- [security-minion]: Double-encoding check is scoped only to parsed.pathname, leaving the query string unguarded.
  SCOPE: src/url-validation.js -- Step 8 of the validation pipeline
  CHANGE: Extend the double-encoding check to cover parsed.search (the query string) in addition to parsed.pathname. The check pattern /%25[0-9a-fA-F]{2}/ should be applied to both. Optionally apply to parsed.hash (fragment) as well, though browsers typically drop fragments before sending requests. The simplest implementation: check the full parsed.href minus the origin, or concatenate pathname + search and apply the pattern once.
  WHY: An attacker who wants to smuggle a double-encoded path traversal or injection sequence into a downstream system may encode it in the query string rather than the path. If the downstream system (or a proxy between the Worker and Browser Rendering) reconstructs the full URL from parts, a %252F in the query string can traverse boundaries that path-only checking misses. Limiting the check to pathname gives a false sense of completeness.
  TASK: Task 1 (implementation prompt, Step 8), Task 2 (test suite -- add cases for %252F in query string)

- [security-minion]: The success result returns only the first resolved IP (ip: firstPublicIP) but does not document which IP index is selected when both IPv4 and IPv6 results are returned, creating ambiguity that could cause the returned IP to differ from the IP actually used by Browser Rendering.
  SCOPE: src/url-validation.js -- Step 9 return value; docs/evolution/0003-url-validation/decisions.md
  CHANGE: The implementation prompt should specify explicitly: "return the first IPv4 address from resolve4 results if available, otherwise return the first IPv6 address from resolve6 results." Do not return a mix without a defined tiebreaker. Document this choice with a SECURITY: comment at the return site, noting that Browser Rendering will independently resolve DNS and may use a different address family. The evolution log decisions.md should capture this as a decision: which IP is returned and why it is informational-only (the TOCTOU gap means it cannot be used for enforcement by the caller).
  WHY: This is primarily a clarity concern that prevents future misuse. If a caller stores the returned ip and later uses it to make security assertions ("this IP was validated"), it needs to match the address family the browser will actually use. Ambiguity here invites future security-relevant bugs when Step 3 wires the module into the capture pipeline.
  TASK: Task 1 (implementation prompt, Step 9 and return value spec), Task 3 (decisions.md)

- [security-minion]: The Loopback-via-CNAME scenario is not documented as an untestable vector -- the test suite documents DNS rebinding and TOCTOU but not the case where a public CNAME resolves to a private A record (e.g., evil.example.com CNAME internal.corp.local A 10.0.0.1).
  SCOPE: test/url-validation.test.js -- describe('untestable vectors (documented)') block
  CHANGE: Add a comment entry in the untestable vectors block: "// - CNAME chains that ultimately resolve to private IPs: the resolvers return only final A/AAAA records, so CNAME bypasses are covered by the IP check, but only if the DNS resolver follows the chain to completion. Custom resolver stubs in production must not short-circuit CNAME resolution." This is not a code change -- it is a documentation addition that ensures the production DNS resolver configuration (resolve4/resolve6 must follow the full CNAME chain) is explicitly called out.
  WHY: The validation is correct for well-behaved DNS resolvers, but a future operator replacing the resolver (e.g., switching from node:dns to a custom DoH implementation) needs to know that CNAME chain completion is a security requirement, not just a correctness requirement. Without this note, the assumption is invisible.
  TASK: Task 2 (test suite, untestable vectors block)
