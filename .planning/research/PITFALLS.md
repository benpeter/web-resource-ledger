# Pitfalls Research — Capture Quality Push

**Domain:** Evidence-grade web capture (Capture Quality Push milestone for WRL)
**Researched:** 2026-04-30

---

## Pitfalls Specific to Evidence-Grade Positioning

These are highest-stakes — they directly attack the product's core value proposition. Anything undermining determinism, signature integrity, audit trail, or capture honesty.

| Pitfall | Severity | Threatens | Warning Signs | Prevention |
|---|---|---|---|---|
| **fflate `zipSync` entry ordering is non-deterministic for numeric-looking keys.** fflate issue [#197](https://github.com/101arrowz/fflate/issues/197) confirms that JS object key enumeration reorders integer-like keys before string keys. Current WACZ paths (`datapackage.json`, `archive/data.warc`, etc.) are all string-like and safe, but adding subresource files with numeric names (e.g., `0001.png`) to the ZIP would silently reorder entries, producing different WACZ bytes for the same content. | CRITICAL | #257 Area 4 | WACZ sha256 changes across identical-input runs; `packages/verify/` CLI verification fails on a WACZ that was valid at creation time. | Pin entry order via an array-based ZIP builder or use `Map` insertion order. Before adding any subresource path to the WACZ, run a determinism assertion: build the same WACZ twice with identical inputs and assert byte-equal output. Add this as a unit test in `test/wacz.test.js`. |
| **WARC record IDs use `crypto.randomUUID()`.** Every `buildWarc()` call produces different WARC-Record-ID headers, different byte streams, different hashes — by design. The bundleHash (which is signed) covers the canonical datapackage, which includes per-file sha256 hashes, so signatures are correct per-capture. But the *non-reproducibility* means two captures of the exact same page will always produce different hashes. This is fine for the signing model but must be understood by anyone designing subresource capture or dedup logic. | MEDIUM | #257 Area 4 | Confusion in tests that assert WACZ identity across runs; false bug reports from users expecting reproducible hashes. | Document explicitly in `warc.js` and in user-facing docs that WACZ hashes are per-capture unique (not content-addressable across captures). Any new subresource capture logic must not assume hash stability. |
| **Accidental bot-protection bypass via UA or stealth changes.** WRL's value as legal evidence requires that captures represent what the site *actually serves*, not content obtained by deception. Any change that makes the headless browser appear more "human" (stealth plugins, UA string mimicking real Chrome, disabling `navigator.webdriver`, Canvas fingerprint spoofing) crosses from "annotation" to "evasion." Sites that detect headless browsers and serve different content are doing so intentionally — WRL must capture what they serve to WRL, not bypass their intent. | CRITICAL | #257 Area 5 | UA string in `captureHeaders()` diverges from `WRL/0.1` identifier; any import of `puppeteer-extra-plugin-stealth` or equivalent; `navigator.webdriver` overrides in `context.addInitScript()`; team discussions framing bot-blocked captures as "bugs to fix" rather than "facts to record." | Hard rule: the `User-Agent` header for both the browser session and the `fetch()` in `captureHeaders()` must always contain `WRL`. No stealth patches, no automation-flag overrides. Area 5 work is annotation-only (enrich metadata with `botProtectionDetected: true` when content looks like a challenge page). Add a CI check that greps for stealth-related imports and `navigator.webdriver` overrides. |
| **Subresource capture breaking signature chain.** If Area 4 adds CSS/JS/image subresources to the WACZ, every additional file is a new WARC record whose content depends on network timing, CDN cache state, and request ordering. Two captures of the same URL seconds apart may include different ad scripts, different CDN-hashed filenames, or different A/B test variants. The WACZ signature covers the *bundle as captured*, so this isn't a signature-integrity problem, but it creates a much larger surface area where "capture fidelity" is hard to define. | HIGH | #257 Area 4 | Subresource count varies wildly across runs of the same URL; WACZ file size explodes beyond R2 budget; `MAX_SUBRESOURCES: 500` hit frequently; Coralogix shows `limit_exceeded` events spiking. | Start with a conservative allowlist of subresource types (stylesheets, images referenced in `<img>` tags, web fonts) rather than capturing all network traffic. Implement a size budget per-subresource and per-WACZ. Log subresource count and total bytes as Coralogix metrics. Gate the feature behind a `captureSubresources: true` option, default off initially. |
| **Timestamp drift between capture and WACZ assembly.** `buildWacz()` calls `new Date().toISOString()` at assembly time, not at navigation time. If the browser render takes 30s and WACZ assembly takes another few seconds, the `captureDate` embedded in the WACZ may differ from the actual moment the page was rendered. For evidence purposes, this gap matters. | MEDIUM | #257 Area 6, #206 | `captureDate` in WACZ differs from the navigation timestamp by >5s; TSA timestamp is >60s after the actual render. | Thread the navigation-completion timestamp from `defaultRenderer()` through to `buildWacz()` instead of using `new Date()` at assembly time. The render stages already track `tNav`, `tSettle`, etc. |

## Pitfalls by #257 Area

### Area 1 — Dynamic content handling

| Pitfall | Severity | Warning Signs | Prevention |
|---|---|---|---|
| **Over-tuning settle heuristic to SPA sites regresses p95 for static sites.** Current `SETTLE_MAX_MS = 3000` / `SETTLE_QUIESCENCE_MS = 500` works for most sites. Increasing the settle window to catch late SPA renders (React hydration, client-side routing) penalizes every capture with a longer floor wait. The 500ms quiescence window already handles the common case; making it 2s "to be safe" adds 1.5s to every fast site. | HIGH | p95 capture duration increases by >1s in Coralogix after deploy; `settleReason: 'idle'` captures show `settleMs` clustered near new ceiling instead of distributed. | Any settle-heuristic change must be gated by before/after p50 and p95 metrics across a diverse URL battery (not just the SPA that motivated the change). Consider per-page-type adaptive settle (detect SPA framework markers before choosing settle strategy) rather than raising the global ceiling. |
| **Infinite scroll triggers unbounded page growth.** `triggerLazyLoading()` has a `MAX_SCROLL_HEIGHT = 12000` guard and checks `currentHeight - initialHeight > MAX_SCROLL_HEIGHT`, but an infinite-scroll page that grows exactly at the scroll rate could keep the loop running until the 90s screenshot timeout. | MEDIUM | `scrollMs` exceeds 10s in Coralogix; `screenshotBytes` spikes for social-media/feed URLs. | Add a hard wall-clock cap to the scroll loop (e.g., 5s) independent of the height guard. Log when the cap is hit so we can distinguish "page was tall" from "page was infinite." |
| **Lazy-load force-eager trick doesn't work for `IntersectionObserver`-only patterns.** The `img.loading = 'eager'` swap in `triggerLazyLoading()` only helps native lazy loading. JS frameworks (React lazy, Next.js Image, custom IntersectionObserver) don't use the `loading` attribute — they swap `data-src` to `src` on intersection. The scroll already triggers these, but the scroll-back-to-top + 500ms pause may cause already-triggered images to be garbage-collected from DOM before screenshot. | MEDIUM | Screenshots show placeholder boxes or broken-image icons for below-fold images on framework-heavy sites; `screenshotBytes` is suspiciously small for image-heavy pages. | After the force-eager step and settle, verify a sample of `<img>` elements have `naturalWidth > 0` before taking the screenshot. If not, wait an additional 500ms. Track this as a Coralogix metric (`lazyLoadIncomplete: true`). |
| **Web font FOUT/FOIT in screenshots.** Playwright's `document.fonts.ready` is not explicitly awaited in the current pipeline. Fonts loaded via `@font-face` may not be rasterized by screenshot time, producing screenshots with fallback fonts that later change — breaking diff-detection for rescans. PR [#31295](https://github.com/microsoft/playwright/pull/31295) in Playwright itself fixed a hang related to `document.fonts.ready` in iframe contexts. | MEDIUM | Screenshot text renders in system fonts (Arial/Times) when the live page uses custom fonts; diff falsely reports "changed" on rescan because fonts loaded differently. | Add `await page.evaluate(() => document.fonts.ready)` after settle and before the before-screenshot, with a 2s timeout. Log font-ready timing as a stage metric. |

### Area 2 — Cookie consent / overlays

| Pitfall | Severity | Warning Signs | Prevention |
|---|---|---|---|
| **Autoconsent cross-origin iframe injection fails silently.** Five `.catch(() => {})` calls in `consent.js` (lines 112, 154, 156, 179, 254) swallow cross-origin frame evaluation errors. This is documented and arguably correct (cross-origin frames *will* reject), but it means CMP providers that run entirely inside cross-origin iframes (Sourcepoint, TrustArc-Frame) may silently fail to get the autoconsent script, and the capture reports `status: 'none'` instead of `status: 'failed'`. | HIGH | Coralogix shows `consentStatus: 'none'` for sites that visually have a consent banner in `screenshot-before.png`; TrustArc/Sourcepoint sites always report no CMP detected. | Add debug-level logging inside the `.catch()` handlers (log the frame URL and error message). This doesn't change behavior but makes the failure visible. Separately, the audit phase should include 5+ sites using each major CMP provider and verify consent detection. |
| **Autoconsent opts out but doesn't close the banner.** TrustArc issue [#706](https://github.com/ghostery/broken-page-reports/issues/706) documents cases where autoconsent "accepts" instead of "rejects" due to CMP-specific bugs. WRL's `captureSettings.consent.result: 'success'` would then be misleading — the consent was "dismissed" but the wrong choice was made. For evidence purposes, this metadata inaccuracy is significant. | HIGH | `captureSettings.consent.result` says `'success'` but `screenshot` (after) still shows a consent banner or the page behavior implies all cookies were accepted. | The audit phase must include visual verification: compare `screenshot-before.png` and `screenshot.png` for consent-banner sites and confirm the banner actually disappeared. Consider adding a post-consent screenshot-comparison check in the pipeline itself (if the before and after screenshots are pixel-identical, log a warning that consent may not have worked). |
| **Non-standard overlays (paywalls, newsletter popups, age gates) are not handled by autoconsent.** Autoconsent covers ~300 CMPs but does not handle paywalls, newsletter signup modals, or age verification gates. These overlays obscure captured content just as much as cookie banners. | MEDIUM | Screenshots show overlays that are not cookie-consent; `consentStatus: 'none'` on sites with obvious overlays. | Out of scope for autoconsent, but Area 2 metadata should distinguish `'noCmpDetected'` from `'nonConsentOverlayPresent'`. A lightweight heuristic (detect `position: fixed` elements covering >30% of viewport after consent) could flag these for metadata without attempting dismissal. Defer actual dismissal to a future milestone. |
| **2s consent timeout is too short for slow CMPs.** Some CMPs (OneTrust, Didomi) load their consent UI asynchronously after page load. The `CONSENT_TIMEOUT_MS = 2000` hard cap means the autoconsent script may not have time to detect a CMP that loads 2.5s after `DOMContentLoaded`. | MEDIUM | `consentStatus: 'timeout'` with `cmp` detected but opt-out incomplete; sites that work in manual browser testing but fail in capture. | The audit should measure consent timing distribution via Coralogix (`consentMs` field). If >10% of captures hit timeout with a detected CMP, consider raising to 3s or making it adaptive (extend timeout by 1s when a CMP is detected but opt-out hasn't completed). |

### Area 3 — Screenshot quality / timing

| Pitfall | Severity | Warning Signs | Prevention |
|---|---|---|---|
| **Changing screenshot timing breaks diff-detection for rescans.** The rescan flow (`diffScreenshot`) compares screenshot *hashes* — any change in screenshot bytes means `changed: true`. If Area 3 changes `deviceScaleFactor`, viewport width, scroll timing, or font-load gating, *every* subsequent capture will diff as "changed" against all prior captures of the same URL, even if the page itself didn't change. This will cause a flood of false-positive change notifications. | HIGH | After deploy, `diffScreenshot.changed: true` for 100% of rescan captures; webhook volume spikes; users report spurious "page changed" alerts. | Screenshot parameter changes must be versioned. Store the screenshot parameters (DPR, viewport, height cap) in `captureSettings` and compare only captures with matching settings. Alternatively, introduce a `screenshotVersion` field and suppress diff when versions differ. Roll changes out with a deprecation period: run both old and new settings in parallel, compare results, then cut over. |
| **4x `deviceScaleFactor` + 8000px `MAX_PAGE_HEIGHT` produces ~120MB uncompressed pixel data.** `1280 * 4 * 8000 * 4 * 4 bytes/pixel = ~655 MB` in raw framebuffer. The PNG compression mitigates this, but Chromium must still rasterize the full page at 4x DPR before compressing. This is already at the edge of Cloudflare Browser Rendering's 128MB Worker memory limit. Increasing `MAX_PAGE_HEIGHT` or DPR further could cause OOM crashes. | HIGH | `render.default.cleanup_fail` errors in Coralogix; browser session crashes (`page crashed`) correlate with tall pages; screenshot timeout (90s) hit on tall pages. | Before changing DPR or height cap, profile memory usage on 10 known-tall pages (news articles, documentation, long-form content). Consider capping at 2x DPR for pages exceeding 4000px height (adaptive DPR). Log `pageHeight` and `screenshotBytes` in capture events to build a baseline. |
| **Scroll-back-to-top 500ms pause is fragile.** The comment in `triggerLazyLoading()` explains: "at 4x scale the bottom of an 8000px page is ~32k pixels that need repainting after scroll position changes." The 500ms constant was tuned empirically. Making it shorter risks blank tiles at the bottom of screenshots (confirmed by [Playwright #20859](https://github.com/microsoft/playwright/issues/20859) and [#5487](https://github.com/microsoft/playwright/issues/5487)). Making it longer adds to every capture's duration. | MEDIUM | Screenshots with white/blank bands at the bottom; intermittent — depends on page complexity and Chromium's compositor scheduling. | If changing the pause, A/B test with a batch of 50+ URLs including tall pages. Compare screenshot bytes and visual inspection. Consider replacing the fixed pause with a compositor-ready signal if Playwright exposes one (currently it doesn't — the `screenshot()` call itself waits for rasterization, but `fullPage: true` has known edge cases). |

### Area 4 — WACZ subresource completeness

| Pitfall | Severity | Warning Signs | Prevention |
|---|---|---|---|
| **Adding subresources to WARC changes record count and order, breaking existing `packages/verify/` CLI.** The verify CLI validates the WARC against the CDXJ index and the datapackage hash chain. Any change to record structure (new record types, new WARC-Target-URI patterns) must be mirrored in the verifier. | HIGH | `wrl-verify` CLI fails on new WACZ files; `npm test` in `packages/verify/` passes but real-world verification fails because test fixtures don't include subresources. | Update `packages/verify/` test fixtures in lockstep with any WARC format changes. Add an integration test that builds a WACZ with subresources and verifies it end-to-end. |
| **ReplayWeb.page can't replay WACZs with non-standard WARC-Target-URI schemes.** WRL uses `urn:wrl:screenshot:before:` and `urn:wrl:screenshot:after:` as WARC-Target-URIs for screenshot records. ReplayWeb.page may not know how to route these URIs during replay. Adding more custom URI schemes for subresources would compound this. | MEDIUM | Users report WACZ files that verify correctly but won't open in ReplayWeb.page; specific resources show 404 during replay. | Before shipping, test every WACZ structure change against ReplayWeb.page (desktop app and embedded `<replay-web-page>` component). Use standard `http`/`https` URIs for subresource WARC records. Keep custom `urn:` schemes only for WRL-specific artifacts (screenshots). |
| **Subresource fetch timing affects WACZ size unpredictably.** If subresources are captured via Playwright's network interception (the existing `context.route('**/*')` handler), they arrive in network order, which varies per run. Two captures of the same page may include different sets of subresources if one run's ad network was slower than another's. | MEDIUM | WACZ file sizes for the same URL vary by >50% across runs; subresource count in Coralogix varies by >20%. | Capture subresources deterministically by parsing the final HTML for `<link>`, `<script>`, `<img>` references and fetching them explicitly, rather than relying on network interception timing. This decouples subresource capture from browser rendering timing. |

### Area 5 — Bot-protection annotation

| Pitfall | Severity | Warning Signs | Prevention |
|---|---|---|---|
| **Bot-detection heuristics false-positive on legitimate content.** `detectRenderFailure()` already checks for blank pages and Chromium error pages but explicitly avoids bot-detection heuristics ("false-positive too easily"). Adding heuristics like "page contains 'Access Denied'" or "page has a Cloudflare challenge" will false-positive on pages that legitimately contain those strings (e.g., a blog post about Cloudflare, an error-page testing tool). | HIGH | `botProtectionDetected: true` on pages that are actually displaying correct content; user trust in metadata eroded. | Use a multi-signal approach: combine title text, body text length, specific DOM structures (e.g., `<div id="cf-wrapper">` for Cloudflare), and HTTP status codes. Require ≥2 signals before flagging. Log the signals that triggered the flag so false positives can be debugged. Never auto-fail a capture based on bot-detection — annotate only. |
| **Bot-detection annotation creates a perverse incentive to "fix" detected captures.** Once the system flags captures as bot-affected, the team will face pressure to "improve" capture quality by bypassing detection — which is exactly what the project's constraints forbid. | MEDIUM | PRs that propose UA changes, stealth patches, or `navigator.webdriver` overrides framed as "fixing Area 5 issues." | Document the bright line in `CLAUDE.md` and the pipeline interface contract: WRL captures honestly. Bot-blocked captures are correctly captured (they capture what the bot sees). Area 5 adds metadata, never changes behavior. Add a CI check for stealth-related code patterns. |

### Area 6 — Render-failure resilience

| Pitfall | Severity | Warning Signs | Prevention |
|---|---|---|---|
| **Partial-capture fallback masks systematic failures.** The current partial-capture path (triggered after 20s nav timeout) degrades gracefully but may hide the fact that an entire class of sites consistently fails. If 30% of captures are partial but the "success rate" metric counts partials as successes, the fidelity problem is invisible. | HIGH | `renderQuality: 'partial'` rate exceeds 10% in Coralogix; `waczStatus: 'skipped'` correlates with partial captures (WACZ is skipped for partials, meaning no signed evidence bundle). | Track partial rate as a distinct Coralogix metric, separate from success/failure. Alert if partial rate exceeds threshold (e.g., 15%). In the audit phase, analyze which URLs produce partials and whether they share a common cause (bot protection, geo-blocking, slow CDN). |
| **Expanding `detectRenderFailure()` to check more failure modes introduces timing sensitivity.** The function runs `page.evaluate()` after settle. If a site's JavaScript replaces the DOM after settle (e.g., delayed client-side redirect), the render-failure check may pass but the screenshot captures a transient state. | MEDIUM | `detectRenderFailure` returns `{ failed: false }` but screenshot shows a blank or redirect page; capture completes but is useless. | Run render-failure detection both after settle and after screenshot (compare DOM state at both points). If the DOM changed significantly between the two checks, flag the capture as `renderUnstable: true` in metadata. |
| **"Site is slow" vs "site blocked us" vs "site is broken" distinction is hard.** The current code distinguishes `totalBytes === 0` (possible bot protection) from timeout-with-content (slow site), but doesn't distinguish a site that returns a 403 + challenge page (bot protection) from one that returns a 403 + "forbidden" page (access control). Both have bytes, both have a non-error DOM. | MEDIUM | `captureHeaders` shows `status: 403` but there's no metadata distinguishing "Cloudflare challenge 403" from "nginx 403 forbidden"; users can't tell if their capture was blocked. | Cross-reference `captureHeaders.status` with `detectRenderFailure` signals. A 403 + Cloudflare challenge DOM = `renderFailureReason: 'bot_protection'`. A 403 + normal content = no flag. Add status code to the render-failure check inputs. |

## Pitfalls Specific to #206 (Pluggable Pipeline)

| Pitfall | Severity | Warning Signs | Prevention |
|---|---|---|---|
| **Interface leaks browser-specific assumptions.** The current `renderer` parameter signature is `(env, url, captureId) => { screenshot, html, partial, render, consent, screenshotBefore }`. The return shape assumes a browser-based pipeline (dual screenshots, consent metadata, render stages with browser-specific timing). A fetch-based pipeline (#143, currently parked) would have none of these. If the interface encodes browser assumptions, adding a non-browser pipeline requires either faking browser-shaped output or changing the interface — both bad. | HIGH | Pipeline interface mentions `page`, `browser`, `playwright`, `screenshot`, `consent`, `screenshotBefore` as required outputs; the fetch-based pipeline has to return dummy screenshots to satisfy the contract. | Define the pipeline output as: `{ artifacts: Map<string, Uint8Array>, metadata: object, quality: 'full'|'partial'|'degraded' }`. Artifacts are named blobs; metadata is pipeline-specific. The orchestrator (capture.js or its successor) maps pipeline output to storage and DB shapes. Screenshots and consent are browser-pipeline-specific metadata, not universal contract requirements. |
| **Refactoring capture.js into a pipeline breaks the existing `renderer` injection used by tests.** `test/capture.test.js` injects a mock `renderer` to bypass real Chromium. If the pipeline refactor changes the injection mechanism, all capture tests break. | MEDIUM | Test suite red after pipeline refactor; temptation to rewrite tests rather than preserve the injection seam. | Preserve a clean injection seam as part of the interface contract. The pipeline factory should accept injectable dependencies (browser session factory, consent handler, etc.) so tests can stub individual pieces without mocking the entire pipeline. |
| **Per-environment pipeline selection via `wrangler.toml` doesn't compose with future per-tenant selection.** If the initial implementation uses a simple env-var (`CAPTURE_PIPELINE=browser`), migrating to per-tenant selection later requires changing every call site that reads the env var. | MEDIUM | `CAPTURE_PIPELINE` env var referenced in 5+ files; adding per-tenant requires touching all of them. | Centralize pipeline resolution in a single factory function: `getPipeline(env, tenantConfig)`. The factory reads the env var today and can read tenant config tomorrow. All other code calls the factory, never reads the env var directly. |
| **Pipeline abstraction encourages premature generalization.** The Helix manifesto says YAGNI. There's exactly one pipeline today (browser-based) and one parked (#143, fetch-based). Designing a generic plugin system for two (or 1.5) implementations is over-engineering. | MEDIUM | Pipeline interface has >10 methods; pipeline registration requires a config file or registry pattern; "plugin" language creeps into the codebase. | The interface should be a single function (or at most a factory + execute). No plugin registry, no lifecycle hooks, no event system. The interface is a contract, not a framework. If the browser pipeline and the (future) fetch pipeline can both be expressed as `async (env, url, options) => result`, the abstraction is right-sized. |

## Cross-Cutting Pitfalls

| Pitfall | Severity | Threatens | Warning Signs | Prevention |
|---|---|---|---|---|
| **Performance budget regression: p95 capture duration.** Every new step in the pipeline (font-wait, extended settle, subresource capture, post-consent verification, render-failure enrichment) adds latency. Individually each is 200-500ms; cumulatively they could add 2-3s to every capture, pushing p95 past the quality gate. | HIGH | All areas | p95 `durationMs` in Coralogix trends upward across phases; `settleMs` + `scrollMs` + `consentMs` + new stages sum exceeds 10s for median sites. | Maintain a performance budget spreadsheet: current p50/p95 per stage, and the budget each area is allowed to add. Measure before and after each area's changes. Any area that pushes p95 up by >500ms must justify or optimize. |
| **Coralogix log volume explosion.** `capture.js` already emits ~15 log events per successful capture (session_acquired, context_ready, nav_success, settle_complete, lazy_load_complete, screenshot_before, consent_result, screenshot_after, content_extracted, complete, plus the success summary). Adding debug-level events for each new feature (font-wait timing, subresource counts, render-failure details, bot-detection signals) could double this. At scale, Coralogix costs are per-GB-ingested. | MEDIUM | All areas | Coralogix daily ingestion volume doubles after deploy; monthly bill spike; log events per capture exceeds 25. | Use severity 3 (info) sparingly for new events — prefer adding fields to existing events over emitting new ones. Add a `capture.detail` composite event that bundles all new diagnostic fields into a single log line. Review log volume in staging before production deploy. |
| **Cloudflare Browser Rendering quotas and pricing.** Paid plan: 10 concurrent browsers, 10 new instances/min, 10 hours/month included, $0.09/hr after. `keep_alive: 120000ms` (2min) in the code means sessions are kept warm for 2 minutes of billable time after each use. If capture volume spikes or settle times increase, browser hours consumed will increase proportionally. The concurrent browser limit (10) is also the queue consumer concurrency ceiling — more concurrent captures = more concurrent browsers. | MEDIUM | All areas | Monthly browser hours exceed 10h; `session pool at capacity` errors in Coralogix; unexpected billing increase. | Monitor browser-hour consumption via Coralogix (log session duration). Consider reducing `keep_alive` to 60s (minimum) if session reuse rate is low. Alert on session-pool-exhaustion events. Before any change that increases per-capture browser time, estimate the monthly hour impact. |
| **Cloudflare Workers CPU time limit.** As of March 2025, Workers have a 5-minute CPU time limit per request. Queue consumers share this limit. The current worst-case pipeline is ~30s wall clock but much less CPU (most time is waiting on browser I/O). However, adding CPU-intensive work (subresource hashing, image processing, DOM analysis) could approach the limit. `sha256()` over a 50MB WACZ is measurable CPU. | LOW | All areas | Queue consumer crashes with "CPU time exceeded" errors; `capture.fail` events with no browser-related error message. | Profile CPU time for the heaviest capture scenarios (50MB page + full subresources + WACZ assembly). Keep CPU-intensive operations (hashing, ZIP assembly) streaming rather than buffered where possible. |
| **Test coverage gap: functional tests pass but fidelity degrades invisibly.** Unit tests with mocked renderers verify pipeline orchestration but cannot detect fidelity regressions (missing fonts, broken lazy loading, consent banner still visible). Integration tests exercise real browsers but typically use controlled test pages, not real-world sites with complex behavior. A change that passes all tests but produces worse screenshots in production is the most dangerous kind of regression. | HIGH | #257 all areas | All tests green but Coralogix shows increased `renderQuality: 'partial'` rate, decreased `screenshotBytes`, or users report visual issues not caught by automation. | The audit phase must produce a **reference corpus**: 20+ real-world URLs spanning every #257 area (SPA, CMP, tall page, image-heavy, bot-protected). Each phase's verification step must capture these URLs before and after changes and compare screenshots visually + by hash. This is not automatable in CI (real-world sites change), but it should be a manual gate at each phase boundary. |
| **Breaking changes to `captureSettings` schema.** `captureSettings` is embedded in signed WACZ bundles and stored in D1. Any schema change (renaming fields, changing `consent.result` values, adding required fields) creates a compatibility gap: old captures have the old schema, new captures have the new schema. Consumers (dashboard, MCP tools, `wrl-verify`, API clients) must handle both. | MEDIUM | #257 Areas 2, 5, 6 | `captureSettings` deserialization fails for old captures; dashboard shows "undefined" for new fields on old captures; API responses include null fields that used to be absent. | Version the `captureSettings` schema (`version: 1` → `version: 2`). Old captures keep `version: 1`. New captures use `version: 2`. All consumers switch on version. Never remove or rename fields within a version — only add. |

## Pitfall → Phase Mapping (for roadmap consumer)

Each likely phase inherits specific pitfall risks. The roadmapper should seed phase-level risk callouts from this list.

**Pre-flight cleanup phase:**
- No pitfalls from this list (the three fixes are surgical and low-risk).

**Audit phase:**
- Build the **reference corpus** (cross-cutting: test coverage gap).
- Measure current baselines: p50/p95 capture duration, partial rate, consent detection rate, log volume per capture, browser hours consumed.
- Identify which CMP providers fail silently (Area 2: cross-origin iframe injection).
- Identify which sites trigger bot-detection heuristic false positives (Area 5).

**Area 1 — Dynamic content handling:**
- Settle heuristic regression (p95 perf budget).
- Infinite scroll loop (scroll wall-clock cap).
- Font FOUT in screenshots.
- Lazy-load incomplete for IntersectionObserver patterns.

**Area 2 — Cookie consent / overlays:**
- Cross-origin iframe silent failure.
- Autoconsent wrong-choice (accepts instead of rejects).
- 2s consent timeout too short.
- `captureSettings` schema versioning.

**Area 3 — Screenshot quality / timing:**
- **Highest-risk for diff-detection breakage.** Any screenshot parameter change invalidates all prior diff baselines.
- Memory pressure at 4x DPR + tall pages.
- Scroll-back-to-top compositor pause fragility.

**Area 4 — WACZ subresource completeness:**
- **Highest-risk for determinism/signature integrity.** fflate ordering, WARC record structure changes, verify CLI compatibility.
- ReplayWeb.page replay compatibility.
- Subresource fetch timing variability.
- WACZ size budget impact on R2 storage.

**Area 5 — Bot-protection annotation:**
- False-positive heuristics.
- Perverse incentive to bypass (accidental bot-protection evasion).
- `captureSettings` schema additions.

**Area 6 — Render-failure resilience:**
- Partial-capture rate masking systematic failures.
- "Slow vs blocked vs broken" classification accuracy.
- Timing sensitivity of expanded render-failure checks.

**#206 — Pluggable pipeline:**
- Interface leaking browser-specific assumptions.
- Test breakage during refactor.
- Premature generalization (YAGNI violation).
- Pipeline selection mechanism composability with future per-tenant selection.

## Open Questions

These need observed-data answers and are deferred to the audit phase or later:

1. **What is the current partial-capture rate in production?** Coralogix query: `event = 'capture.partial'` / total captures. If >10%, Area 6 work should be prioritized above other areas.

2. **Which CMP providers are most common in WRL's capture corpus, and which fail silently?** Requires Coralogix analysis of `consentCmp` and `consentStatus` fields across production captures.

3. **What is the current browser-hour consumption?** Needed to model the cost impact of longer settle times or subresource capture. Available from CF dashboard or billing.

4. **How many production captures hit `MAX_PAGE_HEIGHT: 8000` or `MAX_SUBRESOURCES: 500`?** Coralogix events `render.default.viewport_capped` and `render.default.limit_exceeded` provide this. If the limits are rarely hit, expanding them is low-risk; if commonly hit, the limits are doing real work.

5. **Do any existing WACZ files fail to load in ReplayWeb.page?** The `urn:wrl:screenshot:*` URI scheme is non-standard. Before adding more non-standard URIs, verify existing WACZs replay correctly.

6. **What is the distribution of `settleMs` and `settleReason` across production captures?** If 90% of captures settle in <500ms as `idle`, the settle heuristic is well-tuned and changes should be conservative. If 40% hit the 3s cap, there's headroom for improvement.

7. **Are there production captures where `captureHeaders.status` is 403/503 but `renderQuality` is `full`?** These are likely bot-blocked captures that passed render-failure detection. They're the target population for Area 5 annotation.

8. **What is the `consentMs` distribution for captures with `consentStatus: 'timeout'`?** If most timeouts are at exactly 2000ms with a CMP detected, the timeout is the binding constraint and should be raised. If timeouts are scattered, the problem is detection reliability, not timeout duration.
